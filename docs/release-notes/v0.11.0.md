# 0.11.0 — 2026-09-20

Parity with attenu-guard (Python) 0.17.0. One change, landed in both ports at
once: a verifier no longer reports success on a token it did not fully read.

## What was wrong

`authorityFromPayload` reconstructed the Authority from `details[0]` and never
looked at the rest of the array. A token carrying `agent_delegation` first and a
second authorization detail after it was accepted, and the second entry was
discarded without an error or a warning.

That is fail-open in exactly one direction, and it is the dangerous one. An
ignored entry that **restricts** authority is lost, so the chain permits more
than the issuer allowed. An ignored entry that **grants** extra authority is
harmless, because ignoring it leaves the chain more restrictive. Only the
harmful direction was silent.

Demonstrated end-to-end in the Python port on the released `valid_chain` vector:
a trailing detail carrying `deny_scopes: ["crm.read"]` was discarded, the chain
verified clean, and `permits("crm.read")` returned allowed — the verifier
permitted the action the issuer's own detail forbade.

**RFC 8785 canonicalization is not what stops this.** Re-serializing the payload
through the canonicaliser produces a token the old verifier accepted; only a
naive `JSON.stringify` was caught, and it was caught as `non_canonical`, which
proves nothing about detail types. `test/unknown-detail-types.test.ts` asserts
the refusal reason is never `non_canonical`, so a future change cannot let
canonicalization quietly stand in for the real rule.

## Why it mattered more than a tidiness bug

The Internet-Draft points implementers at exactly this route. The last paragraph
of "Scope Syntax and Wildcards" says other authorization detail types, if
defined, specify their own scope semantics — so a deployment carrying its own
policy vocabulary as a second detail type was being told to take a path that
failed open in both reference implementations.

## It was worse than the array

A code review of the first fix found it stopped at the array boundary. The
identical fail-open was still live inside a **single** `agent_delegation` entry,
because the loader cherry-picked `scopes` and `constraints` and discarded every
other member — including `actions`, `locations`, `datatypes`, `identifier` and
`privileges`, the RFC 9396 section 2 common members of any authorization detail
object, and `critical`, whose entire meaning is "do not ignore me".

One level deeper again, a constraint object carrying two typed values kept one
and dropped the other: `{"key":"max_rows","max":100,"min":9999}` became
`{"key":"max_rows","max":100}`, byte-identical to a constraint that never
carried a floor.

## The rule now

Three levels, one principle: **refuse what we would only partly read.**

1. More than one authorization detail → `malformed`. Two `agent_delegation`
   entries are refused for a second reason: the draft never says which element
   to take, so taking the first silently nominated a winner the document does
   not.
2. A member inside the `agent_delegation` detail beyond `type`, `scopes` and
   `constraints` → `malformed`.
3. A constraint object that does not survive a parse-and-re-emit round-trip →
   `malformed`.

Every message names what could not be evaluated.

An unrecognised constraint **type** is deliberately not caught by rule 3.
`UnknownCeiling` preserves its whole object, so it round-trips and still routes
to the fail-closed path the draft requires. Turning those into a parse error
would lose the deny.

**Refusing is the loosenable direction.** If a future revision defines
ignorable/critical marking, in the spirit of RFC 9396, accepting more is a
backward-compatible change; starting permissive and tightening later would not
have been.

## Migration

This is a wire-behaviour change: a token that verified before is refused now.

No fixture under `test/fixtures/vectors/` carries more than one authorization
detail, and the library has never emitted more than one. If you mint tokens
elsewhere and put more than one detail in them, they are now rejected as
`malformed`, with the unevaluated entries named in the message.

## Verification

- **383 of 383 tests pass, zero skipped** — including the Python interop suite,
  run against the patched Python source rather than the published wheel.
- New `test/unknown-detail-types.test.ts` (11 tests), each driving the real
  `load()` entry point over the released vector, with a control that re-signs
  the leaf unchanged so a rejection cannot merely mean the test signs badly, and
  an assertion that the refusal reason is never `non_canonical`.
- Both ports were checked directly to accept and refuse the **same eight cases**
  byte-for-byte through `load()`, on the same chain and the same bytes:
  unmodified, a second detail entry, a second `agent_delegation` entry,
  `deny_scopes` inside the detail, `actions` inside the detail, `critical`
  inside the detail, a second typed value inside a constraint, and an unknown
  member inside a constraint.
