# 0.14.0 — TBD

Parity with attenu-guard (Python) 0.20.0. The -02 revision of the Internet-Draft
(draft-asor-wimse-agent-delegation-chain-02), as an opt-in profile beside the -01, and its
vector set, vendored. The -01 stays the default on every path. Cross-language fixes ride along
(attenu-ops #127).

This package verifies Delegation Chains and mints none: `src/wire.ts` exports `load` and no
serializer. Everything below is the verifier's side and the in-process `Authority` and `Guard`.

## The -02 profile, opt-in

Pass `{ draft: "02" }` to `load`, `profile: "02"` to `new Authority`, or `"02"` as the second
argument of `Authority.fromWire`. Without it, every call takes the -01 path it took in 0.13.2,
and the twenty published -01 vectors verify exactly as before. A chain minted under one profile
is `malformed` under the other, and a meet across profiles is refused as `not_narrower`.

What the -02 adds, as this package implements it:

- **Who acts, for whom.** The Principal is in `sub` and must be identical at every hop
  (`principal_altered`, checked after the depth checks); the Acting Agent is in `client_id`.
- **Audience.** `aud` is a string or a non-empty array (null is `malformed`), checked against
  `load`'s `audience` option and by `VerifiedChain.permits`, which denies `audience_mismatch`
  when no audience was supplied at load or at the call.
- **Holder binding claim.** `cnf` on every token, carrying `jkt`, `jwk` or `x5t#S256`. Its
  presence and shape are checked; steps 6 (holder binding) and 7 (status list) are not
  performed.
- **Accepted algorithms.** Step 1 takes a list (`acceptedAlgs`, an array, defaulting to the
  signer's own algorithm) and denies an off-list `alg` even where the signature verifies. Under
  `"01"` the list is honoured only when given.
- **Three scope forms.** Literal, wildcard and opaque, with no case folding and no trailing
  newline. An opaque scope is covered only by a byte-identical child scope, never by a
  wildcard.
- **Constraint types.** `max_lifetime` and `max_subtree` beside the per-action `max`, with no
  inference across types; `CallLimit` emitted as `max_lifetime` and `EgressRank` with its
  `order`; one constraint per (key, type).
- **Closed objects.** Closed constraint objects and exactly one `agent_delegation` detail,
  classified at parse, before step 1.
- **Step 4 per hop** on scopes, constraints and `del_max_depth`, never the derived lifetime, so
  a later child `exp` is `expired`.

The -02 rules live in `draft02`: `classifyScope`, `scopeCovers`, `Max`, `Min`, `MaxLifetime`,
`MaxSubtree`, `Rank`, `ceilingFromWire02` and `ceilingToWire02`.

## Running totals come only from the trusted channel

A cumulative constraint bounds a running total, and the -02's step 8 says one whose total is
held nowhere denies. Under `"02"` a total comes only through the `totals` option of
`Authority.permits`, `VerifiedChain.permits`, `Guard.check` and `Guard.wouldAllow`, never from
the request context:

- A cumulative constraint reads the trusted totals only, and a per-action constraint reads the
  request context only. The two are never merged, so no field name can make one stand in for
  the other.
- `totals` may name only the total fields of the cumulative constraints held, and is refused
  under `"01"`.
- The guard's call meter is the only source of a `max_calls` total, and never of a subtree
  total. A per-action `max` on a `max_calls` key is refused.
- A cumulative bound with no total held denies.

These rules are the outcome of four rounds of independent security review of the Python
implementation, described round by round in its 0.20.0 release notes. Each finding is a test
in `test/draft02-review-fixes.test.ts`, case for case the Python suite's
`tests/test_draft02_review_fixes.py`. The fourth round found no blocker and no major.

## Known limitation: legacy and generic ceilings do not pair

Under `"02"`, a legacy fixed-key ceiling and the generic ceiling of the same type on the same
key (`RowLimit` beside `Max("max_rows", ...)`) share the (key, type) pair but are different
classes, so neither subsumes the other, and a delegation across them is refused as
`not_narrower` even where the values narrow. That is a false deny, never a false allow. Build
both sides of a delegation from the same form. The Python implementation has the same
limitation.

## The -02 vector set, vendored

`test/fixtures/vectors/draft02/` holds the 35 -02 vector files, byte for byte the Python
package's, copied by `tools/gen_fixtures.py`. Every vector scores here to its declared Table 2
outcome under the vector's `verifier` block, and every one of the 35 chains is rebuilt here from
the same `Guard.issue` / `delegate` calls as the Python generator and compared byte for byte. A
run of the set scores steps 1 to 5 and the audience half of step 8, plus the parse-time rules,
under the HS256 single-signer public-test-key profile; steps 6 and 7 are not scored. The twenty
-01 files are unchanged.

## Also fixed: differences from the Python implementation

**A `null` `scopes` or `constraints` list was read as empty under the -01 profile.** The Python
implementation refuses both as `malformed`. Neither widened authority: an empty scope list
permits nothing, and a child whose null constraints were read as none still failed subsumption
under a constrained parent. Both lists are now read as arrays or refused, on both profiles,
with the Python implementation's messages.

**An object `scopes` was refused only by accident.** A `Set` cannot iterate an object, so the
token was refused with a message about iteration, while the Python implementation verified it
(fixed there in 0.20.0). It is now refused by rule: `scopes is an object, not an array`. A scope
member that is not a string is refused with `scopes must be an array of strings`, in both
implementations.

**The safe-integer rule is now the same in both.** This package always refused a number whose
value is an integer past ±(2^53 - 1), whatever its lexical form (`1e+308`,
`9007199254740992.0`): `malformed` at token parse and `hash mismatch` in a ledger entry. The
Python implementation refused only an integer literal until 0.20.0, so a ledger entry carrying
`1e308` verified there and failed here. No behaviour changes in this package;
`test/wire-parity-127.test.ts` pins the rule on both paths so neither implementation moves away
from it. The rule is stricter than RFC 8785, which serializes any finite double (`1e+30` as it
is): it comes from the -02's Section 3 sentence, applied by value, and under the -01 it is the
library's own rule. The published vectors test only the integer literal.

**`Guard.check` threw with nothing recorded on a context the ledger cannot hold.** A context
number of 2^53 or more (`spend: 1e21`, a nanosecond timestamp), a NaN, an infinity or a lone
surrogate threw a `CanonicalizationError` out of `check` and appended nothing. Adapters fill the
context from tool arguments, so a model-sent value became a refusal nobody could see. It is now
a deny on the record: `no_authority` on the constraint `context`, disposition `unresolved`, the
context left out of the row and the meters as they were. `check` records it and returns it as
it returns every deny; `enforce` throws it as `AuthorityDenied`. `wouldAllow` reports the same
deny and writes nothing. For
`spend: 1e21` the message is:

```
context not representable: integer 1e+21 exceeds the safe range ±9007199254740991 for a binary64 signing surface (RFC 8785 numbers are IEEE 754 doubles)
```

The Python implementation makes the same change in 0.20.0, with the same message.

## Migration

Nothing changes unless you pass the `"02"` profile, with two exceptions:

- Under `"01"`, a token or an authority object whose `scopes` or `constraints` is `null`, or
  whose `scopes` is not an array of strings, is refused as `malformed` where a `null` list used
  to be read as empty. This package never wrote one.
- A `check` whose context the ledger cannot hold is recorded as a deny and throws
  `AuthorityDenied`, where it threw a `CanonicalizationError` with nothing recorded.
